## METHOD CORRECTION (mine)
  My first count assumed every thunk's two quads sat at +0x30/+0x40. That is
  unsound: each thunk embeds .asciz "<name>", so thunk size varies with name
  length. I re-measured WITHOUT any layout assumption -- scanning the section
  for 8-byte-aligned qwords whose value falls inside the image VA range, then
  checking each against the .reloc directory.
  The corrected method returns THE SAME NUMBERS:
      absolute image-range qwords in .autoload_text : 424
      WITH DIR64 base relocation                    :  10
      WITHOUT                                       : 414
  So the figure stands, but it now rests on a sound derivation.

## HYPOTHESIS TESTED AND REFUTED: '10 == number of distinct DLLs'
  distinct autoloaded DLLs in autoload.cc : 21
  distinct ..._info symbols in the image  : 21
  (kernel32 ntdll advapi32 user32 secur32 netapi32 ws2_32 wldap32 shell32
   ole32 psapi pdh mpr iphlpapi gdi32 dnsapi authz userenv winmm KernelBase)
  21 != 10, so 'one base relocation per unique target symbol' is WRONG.

## WHAT THE SURVIVORS ACTUALLY ARE
  At least one survivor is a genuine thunk slot: RVA 0x21bdd0 belongs to
  _win32_waveOutClose (thunk at 0x18021bd90) and holds 0x18021bd98, the
  address of its 1b loader stub -- i.e. exactly the same construct as the
  414 that were dropped. So the linker emits a base relocation for SOME
  instances of a construct and drops it for others. The discriminator is
  STILL NOT IDENTIFIED. Reported as an open question, not guessed at.

## BUT THE PRIMARY DEFECT IS UPSTREAM OF ALL OF THIS
  x86_64 and aarch64 emit the SAME two absolute quads per thunk, and a
  sibling confirmed both targets emit ADDR64 object relocations for them.
  The construct is upstream Cygwin design, not an ARM64 port artefact.
  It is safe upstream because the Cygwin runtime DLL is NEVER RELOCATED:
  fork() copies the address space and requires the DLL at the same address
  in parent and child.

  OUR LINK ENABLED ASLR:  DllCharacteristics 0x0160
      HIGH_ENTROPY_VA SET / DYNAMIC_BASE SET / NX_COMPAT SET
  and the image was duly relocated to 0x00007FFDAD3D0000.
  Makefile.am passes no --disable-dynamicbase; modern binutils defaults it on.

  Relinking with -Wl,--disable-dynamicbase -Wl,--disable-high-entropy-va:
