## WHY IT MATTERS
  The aarch64 thunk (autoload.cc LoadDLLfuncEx3) is:
      ldr x16, 3f      // load the resolved-address slot
      br  x16          // branch to it
    1: <loader stub>
    2: .quad .<dll>_info      // info block pointer
    3: .quad 1b               // initially points at the loader stub

  Both quads are ABSOLUTE addresses. The image is ASLR-relocated at load
  time -- observed base 0x00007FFDAD3D0000 vs preferred 0x180000000 -- so
  without a DIR64 base relocation each slot still holds a PREFERRED-BASE
  address after loading. The very first call to any affected autoloaded
  function therefore branches into unmapped memory.

  This is consistent with the observed post-TEB-fix fault:
      0xC0000005 ACCESS_VIOLATION EXEC, PC itself invalid
  i.e. a branch to a bad code pointer rather than a null dereference.
