## WHY THE +0x0C OBSERVATION IS NOT DIAGNOSTIC
  +0x08 handle = 0            -> 00 00 00 00 00 00 00 00
  +0x10 here   = .long -1     -> FF FF FF FF
  ANY 8-byte window starting at +0x0C therefore reads 0xFFFFFFFF00000000.
  That is a property of the DATA, not evidence that a consumer reads there.
  The reporter's own disclosure that this byte pattern occurs 13 times in
  .data points the same way: the value is common, not diagnostic.
  (Independence check per the new rule: that observation was taken by
  reading bytes at a virtual address with no RVA arithmetic, so it does NOT
  share the ImageBase input that invalidated my relocation work. Its
  MEASUREMENT is sound; its INTERPRETATION is unsupported.)

## SECOND HYPOTHESIS I RAISED AND ALSO REFUTED: the 128-bit return ABI
  dll_chain assumes a two_addr_t (__uint128_t) comes back in x0/x1:
        dll_chain:  mov x30, x0 ; br x1
  AAPCS64 returns 128-bit integers in x0:x1, but the MICROSOFT ARM64 ABI
  returns anything over 8 bytes INDIRECTLY via a hidden pointer in x8. If
  GCC followed the MS rule, x0 would be a buffer pointer and x1 garbage --
  and 'br x1' would be an EXECUTE fault to a structured-looking value,
  which is exactly the observed signature.

  TESTED by compiling a 128-bit-returning function with the real cross:
      caller:  mov x0, 0x1111111111111111
               mov x1, 0x2222222222222222
               b   use
  x0/x1, no x8 anywhere. GCC uses AAPCS here, so dll_chain's assumption is
  CORRECT. std_dll_init sets ret.high=func (-> x0) and ret.low=dll->init
  (-> x1); dll_chain sets x30=func and branches to dll->init. Sound.
