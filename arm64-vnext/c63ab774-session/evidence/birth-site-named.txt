## THE INSTRUMENT -- A ZERO-COST RIDER, NOT A NEW HARNESS
  I had hit a throughput wall trying to breakpoint cstrdup (called too often;
  each hit costs a disarm/advance/re-arm round trip). A sibling supplied the
  fix: DON'T breakpoint cstrdup at all -- WALK THE FRAME from the birth probe
  that already works, at the ONE birth that matters.
  AAPCS64: [x29] = caller's frame pointer, [x29+8] = caller's return address.
  This follows directly from my own correction that LR at a post-prologue
  store is NOT the caller (it pointed inside _cmalloc, clobbered by the SRW
  lock call). THE RULE: on ARM64, never read LR for a caller -- walk [x29+8].
  Three pointer chases in the existing handler. No new breakpoint, no fifth
  harness, and it worked on the first run.

     READ   Bcr[3] = 0x4     Bvr[3] = 0x0

## AND MY VERIFICATION CHECK WAS WRONG IN EXACTLY THE WAY I HAVE BEEN

## munge_threadfunc ELIMINATED BY VALUE SHAPE -- BUT IT CARRIES A REAL LATENT
## DEFECT THAT SHOULD BE RECORDED SEPARATELY.
  Proposed candidate (init.cc:31): runs on every DLL_THREAD_ATTACH, walks the

  and PATCHES stack entries. It executes on the new thread inside my bracket,

  The write at init.cc:61 is

  threadfunc_fe is a FUNCTION -- 't threadfunc_fe(void*)' at 0x1800d2980,
  i.e. a CODE pointer inside msys-2.0.dll, which at runtime sits around
  0x7FFDB9xxxxxx (~140 TiB). The observed wild value is ~512 GiB AND IS
  EXACTLY EQUAL TO THE MAIN THREAD'S TEB. Two quantities differing by ~280x,
  where one of them matches a different known value to the byte.
  So munge_threadfunc's patch is not this store.

## BUT THE STRUCTURAL CONCERN IN IT IS GENUINE AND WORTH FLAGGING ANYWAY
  The indices in threadfunc_ix[] are computed ONCE -- the scan at lines 37-41
  is guarded by 'if (!threadfunc_ix[0])' -- on whichever thread runs first,
  as OFFSETS FROM THAT THREAD'S FRAME:
      threadfunc_ix[i++] = peb - ebp;
  and are then REUSED on EVERY SUBSEQUENT THREAD at line 61 as offsets from
  THAT thread's frame:
      ebp[threadfunc_ix[i]] = (char *) threadfunc_fe;
  The scan bound is 'peb < top' where top is StackBase, so an index may be as
  large as the distance from the recording thread's frame to its stack base.
  IF FRAME DEPTHS DIFFER BETWEEN THREADS -- and there is nothing guaranteeing
  they do not, least of all across a new architecture's differing prologues --
  ebp[threadfunc_ix[i]] WRITES AT AN ARBITRARY DISTANCE FROM THE CURRENT
  FRAME, AND CAN LAND AT OR PAST StackBase.
  On THIS memory layout StackBase == CYGHEAP_STORAGE_LOW, so 'past StackBase'
  means 'in the cygheap header'.
  There is no bounds check on the write; only the ORIGINAL SCAN was bounded.
  I am NOT claiming this is our defect -- the value refutes it. I am recording
  it because it is a real hazard of exactly the class we are hunting, in the
  same window, and it would be missed by anyone who eliminated the function
  and moved on.

## THE TWO REMAINING ARM64-ASM CANDIDATES ARE BOTH ELIMINATED -- MEASURED
  Proposal: the bug lives in one of the ARM64 replacements for upstream's
  '#error unimplemented for this target' sites, specifically one that handles
  BOTH the TEB and StackBase with the store/load roles swapped. Named
  candidates: config.h:42 (__getreent) and create_posix_thread.cc:103
  (pthread_wrapper's stack switch).

  1. __getreent -- ALREADY ELIMINATED BY RUNTIME MEASUREMENT (returns
     StackBase - 12800 = 0x7ffffce00, matching x86_64's value exactly).

  2. pthread_wrapper -- ELIMINATED TWICE OVER.
     (a) IT DOES NOT RUN IN THIS WINDOW. cygthread creates its thread with
         plain CreateThread (cygthread.cc:299: 'CreateThread (&sec_none_nih,
         0, is_freerange ? simplestub : stub, ...)'), NOT create_posix_thread.
         So pthread_wrapper is not on the path at all for the sig cygthread.
     (b) THE ASM IS CORRECT ANYWAY. Read it in full (create_posix_thread.cc
         102-124):
            ldr x9, [WRAPPER_ARG, #24]   // stackbase
            mov x10, CYGTLS_PADSIZE
            sub x9, x9, x10              // stackbase - 12800
            and x9, x9, #-16             // AAPCS64 16-byte alignment
            mov sp, x9
            mov x29, #0
         It SUBTRACTS the pad, aligns, and switches sp. IT NEVER TOUCHES x18
         AND PERFORMS NO STORE AT ALL -- so it cannot be a swapped-operand
         TEB store. The x86_64 branch above it does the same thing with the
         same sense.

  So the 'sealed-port ARM64 asm got the operands backwards' hypothesis has no
  surviving site: of the four #error locations, two are the linker script and
  _cygtls::lock, one is __getreent (measured correct), and one is
  pthread_wrapper (not on the path, and correct).
