## THE INSTRUMENT -- READ AT KNOWN POINTS, NEVER CAPTURE A WRITE
  At msys-2.0.dll RVA 0xA8FF8 the instruction is
      str x0, [x5, #8]        ; rvc->prev = cygheap->chain   (cygheap.cc:397)
  so at that PC, x5 is the entry being born and x0 is the value about to
  become its prev. A CODE breakpoint there answers the question straight out
  of the registers.
  Bcr[0]/Bvr[0] carry the probe and Bcr[1]/Bvr[1] the PC+4 advance, so the two
  never contend. DBGBCR = E|PAC(EL0)|BAS(0xF) = 0x1E5.

## RESULT -- ALL FOUR BIRTHS CAPTURED, NO GAPS
   [1] entry(x5)=0x8000048A0   prev-to-store(x0)=0x0                correct
   [2] entry(x5)=0x8000050B0   prev-to-store(x0)=0x8000048A0        correct
   [3] entry(x5)=0x8000068C0   prev-to-store(x0)=0x8000050B0        correct
   [4] entry(x5)=0x8000068F0   prev-to-store(x0)=0x8000341000       *** WILD ***

## VERDICT: CASE (a)
  cygheap->chain WAS ALREADY WILD WHEN ENTRY 0x8000068F0 WAS BORN. _cmalloc
  read a clobbered head and faithfully copied it into the new entry's prev.
  Case (b) -- the slot being overwritten after birth -- IS ELIMINATED.

## THEREFORE THE FOREIGN STORE IS BOUNDED BY TWO CONSECUTIVE _cmalloc CALLS
  It happens AFTER 0x8000068C0's birth (at which point chain was correctly
  set to 0x8000068C0) and BEFORE 0x8000068F0's birth. That is the tightest
  possible bound short of the instruction itself: the interval between two
  adjacent allocations.

## AND THE INSTRUMENT SUCCEEDED EXACTLY WHERE THE WATCHPOINT FAILED
  The hardware DATA watchpoint on cygheap+8 MISSED these same three births --
  they fell in its trace gap, coinciding with a burst of five LOAD_DLL events
  and a thread creation. The CODE breakpoint caught all four with no gaps.
  So the limitation is specific to data watchpoints on this platform, not to
  debug registers in general. That is a reusable capability finding:
  WHEN A DATA WATCHPOINT GOES QUIET ACROSS DLL LOADS, A CODE BREAKPOINT ON THE
  STORING INSTRUCTION IS AN EQUIVALENT AND MORE RELIABLE INSTRUMENT.
  It also vindicates the advice to read at known points rather than capture
  writes -- the design was suggested statically and it worked first time.

## WHAT IS STILL NOT KNOWN

  NOT name the instruction. The faulting PC is still required.

## __getreent() ELIMINATED AS THE WRITER (a candidate from the fork-diagnosis session)
  The candidate was reasonable: config.h has '#error unimplemented for this
  target' for non-x86_64, so the ARM64 port must override it, and _my_tls is
  computed FROM StackBase -- which is exactly 0x800000000, so cygheap+8 IS
  StackBase+8. A sign or offset error there would land precisely on the slot.

  MEASURED -- the implementation in my tree:
     __asm __volatile__ ("mov %0, x18" : "=r" (__teb));   /* TEB */
     ret = *(char **) (__teb + 8);                        /* NT_TIB.StackBase */
     return (struct _reent *) (ret - __CYGTLS_PADSIZE__);
  THE OFFSET IS NEGATIVE. _my_tls = StackBase - 12800, and sizeof(_cygtls) is
  5016, so the struct occupies [StackBase-12800, StackBase-7784] -- entirely
  below the cygheap with 7784 bytes of headroom. It cannot reach StackBase+8.

## WHY NOT SINGLE-STEP (the suggested next instrument)
  Single-stepping [3]->[4] would have been correct in principle but is not

  2. THE HEAD IS STILL CORRECT (0x8000068C0) IMMEDIATELY AFTER THE NEW THREAD

## PRIME SUSPECT, STATED AS A HYPOTHESIS NOT A FINDING
  The thread created at code=2 tid=50920. It is created during setup_cygheap,
  before the pwdgrp path (which is separately proven not to run yet), and the
  head goes wild across its startup.
  A MECHANISM THAT WOULD FIT: every thread's _cygtls lives at ITS OWN
  StackBase - __CYGTLS_PADSIZE__. The MAIN thread's StackBase is exactly
  0x800000000 == CYGHEAP_STORAGE_LOW. If a new thread's _cygtls base were
  computed from the WRONG StackBase -- the main thread's rather than its own --
  writes intended for _cygtls would land at or above 0x800000000, i.e. in the
  cygheap header.
  I HAVE NOT TESTED THIS. Against it: _cygtls::init_thread memsets 5016 bytes
  to ZERO, which would zero the chain and the buckets rather than store a
  pointer, and the buckets are demonstrably intact. So if the new thread is
  the writer, it is via some other store, not the memset.
  NOT A FINDING. The bracket is measured; the mechanism is speculation.

## A CLAIMED sigfe.s / __getreent CONTRADICTION DOES NOT EXIST -- MEASURED
  The lead: sigfe.s allegedly uses 'mrs x16, tpidr_el0' while __getreent()
  uses 'mov x18', so if the two ever disagree __getreent returns a bogus base.
  MEASURED in my tree:
     generated sigfe.s:  'mov x16, x18'        x4
                         'mrs ... tpidr_el0'   x0
        its own header comment reads:
        'TEB access: mov x16, x18 then ldr from [x16, #8]'
        'x18 is the platform register - READ ONLY, never written'
     linked new-msys-2.0.dll: tpidr_el0 occurrences in the ENTIRE image: 0
  NOT ONE tpidr_el0 INSTRUCTION EXISTS IN THE LINKED IMAGE. sigfe.s and
  __getreent both use x18, so they agree and cannot disagree. The 'if they
  ever disagree' branch has no premise.

## WHY THE CLAIM WAS REASONABLE ANYWAY -- AND THE GENERAL LESSON
  'mrs tpidr_el0' WAS in this tree earlier today. The original __getreent()
  used it under a comment asserting it was the TEB register, which is false on
  Windows on Arm. I proved that by executing raw AArch64 instructions in RWX
  memory: tpidr_el0 reads 0, x18 holds the TEB. The fix went into config.h and
  six gendef sites and took the count from 520 to 0.
  SO THE CLAIM ACCURATELY DESCRIBES A REAL HISTORICAL STATE OF THE TREE, JUST
  NOT THE CURRENT ONE.
  GENERAL LESSON WORTH RECORDING: a lead derived from source that has since
  changed looks perfectly sound and is unfalsifiable against the running
  binary -- the reader has no way to know their copy is stale. This is a
  sibling of the artefact-identity problem (verifying a binary that was
  rebuilt underneath you), but on the source side, and it is why 'measured in
  the linked image' beats 'read in the source' whenever the two can be
  compared.

## __getreent() EXONERATED BY DIRECT RUNTIME MEASUREMENT
  The challenge was well-posed: verifying that the SOURCE contains the
  subtraction is not the same as verifying the EMITTED CODE performs it, nor
  that the RUNTIME VALUE is right. Those are three separate claims and only
  the first had been checked. Also correctly noted: the sealed port has no
  ARM64 __getreent at all (#error unimplemented), so this is new port code,
  exactly the kind that can get arithmetic wrong while x86_64 stays correct.

  MEASURED -- built rung11.exe, which reads x18 and [x18+8] itself and calls
  __getreent(), in a live ARM64 process:
     x18 (TEB)         = 0xcbc3c78000
     StackBase [x18+8] = 0x800000000
     __getreent()      = 0x7ffffce00
     difference        = 12800
  THE SUBTRACTION IS PERFORMED. The difference is exactly
  __CYGTLS_PADSIZE__ = 12800, so __getreent() returns 0x7ffffce00, not the raw
  StackBase. The hypothesis predicted 0x800000000 for the defective case; the
  measurement is the healthy value.

  AND IT MATCHES x86_64 EXACTLY. The corroborating datum offered with the
  challenge was that on x86_64 the entry at 0x8000050B0 holds 0x7FFFFCE00 at
  data+0x10 -- the healthy _my_tls pointer. ARM64's __getreent() returns
  0x7ffffce00. IDENTICAL ACROSS ARCHITECTURES, which is the strongest possible
  form of this negative: not merely 'plausible on ARM64' but 'the same number
  the working architecture produces'.

  ALSO CONFIRMED IN PASSING, by the program reading it directly rather than by
  inference: the main thread's StackBase IS 0x800000000, i.e. exactly
  CYGHEAP_STORAGE_LOW. So cygheap+8 really is StackBase+8. That adjacency is
  real -- it is just not reached via __getreent.

## A CORRECTION OF A CORRECTION: 'THE HEAD IS VALID, SO IT WAS NEVER CORRUPT'
## DOES NOT FOLLOW. A RESTING VALUE IS NOT A HISTORY.
  A separate probe walked the chain on ARM64 and found cygheap->chain valid
  (0x800021AD0), 43 clean entries, and the wild prev at 0x8000068F0. From the

## A RULE, NOT A LESSON: THE TWO CANDIDATE STORES ARE INDISTINGUISHABLE BY SHAPE
  My v2 naming attempt reported base+0xA9000 as the foreign store, which is
  the LEGITIMATE 'cygheap->chain = rvc'. I recorded that as an incomplete
  exclusion list. A sibling sharpened WHY, and the sharper form is a rule:
     0xA8FF8  str x0, [x5, #8]     rvc->prev = cygheap->chain
     0xA9000  str x5, [x2, #8]     cygheap->chain = rvc
  BOTH ARE 'str ..., [..., #8]'. So any capture filter phrased as 'a store to
  offset +8' CANNOT distinguish the foreign store from the legitimate one BY
  SHAPE AT ALL. The exclusion must be BY RVA.
  That is not a mistake I happened to make; it is a property of the
  instruction pair, and it would catch anyone using a pattern-based filter.

## AND A GENERAL TEST-DESIGN POINT WORTH KEEPING
  For any candidate buffer, test the wild value for CONTAINMENT in
  [base, base+size), not EQUALITY with the base. An interior pointer
  mis-stored is the realistic shape; equality with a base would be the
  surprising outcome and would point at a different mechanism.

  (observed: LR values 0xA8F2C and 0xA8F84, both inside _cmalloc itself).

  RESULT: the run does not complete. cstrdup is called frequently, and every
  hit costs a disarm / advance-breakpoint / re-arm round trip through the
  debug loop. The run was still going after ten minutes and I stopped it.
  NOT A PLATFORM LIMIT -- a throughput limit of my single-stepping advance.
  A better design would filter in-process, or breakpoint the specific
  _cmalloc(HEAP_STR,...) call site rather than all of cstrdup, or capture
  only the Nth hit.

  I am recording this rather than iterating further: this is the fifth
  harness iteration on the naming problem, and the earlier rule applies --
  if a fifth attempt is worth running it is worth running deliberately rather
  than on momentum.

## WHAT THE FAILED ATTEMPT DID ESTABLISH
  LR at the 0xA8FF8 probe is NOT the caller -- it points inside _cmalloc
  (0xA8F2C / 0xA8F84), because _cmalloc calls the SRW lock before that store.
  So any future attempt to name a caller must break at a function ENTRY, or
  walk the frame, rather than reading LR at an arbitrary mid-function point.
  That is worth knowing before someone reads the existing LR values as caller
  addresses -- they are not.

## USERNAME-LENGTH DISCRIMINATOR: THE VICTIM MOVES, THE TARGET DOES NOT.
## AND THE PROPOSED INTERPRETATION OF THIS TEST IS WRONG.
  Proposed test: run with a different-length username; if the corrupt slot
  moves the writer is allocation-relative, if it stays it is an absolute
  address. cygheap_user::init reads USERNAME from the environment, so this is
  settable without a rebuild.

  MEASURED:
     USERNAME='crutkasLocal' (12 chars) -> corrupt entry 0x8000068F0
     USERNAME=54 chars                  -> corrupt entry 0x800006930
     shift = 0x40 = 64 bytes
  Consistent with the username string moving from bucket_val[0]=32 to
  bucket_val[2]=64 (+32) across two allocations, e.g. USER and USERNAME.

  THE CORRUPT ENTRY MOVES. But the proposed inference does not follow.

## WHY THE INFERENCE FAILS -- IT CONFLATES THE VICTIM WITH THE TARGET
  Case (a) is already MEASURED: the foreign store lands on cygheap->chain at
  0x800000008 -- a FIXED address -- and whichever entry is born NEXT inherits
  the wild head as its prev. So the CORRUPTED ENTRY is simply 'whatever is
  allocated next', and it necessarily moves whenever the allocation layout
  moves. THE VICTIM MOVING IS EXACTLY WHAT AN ABSOLUTE-ADDRESS WRITER
  PREDICTS, so this test cannot distinguish the two hypotheses it was designed
  to separate.
  The store target has been directly observed at the fixed address: sampling
  showed cygheap+8 itself going from 0x8000068C0 to a wild value and back.

## WHAT THE TEST DOES ESTABLISH, AND IT IS WORTH HAVING
  THE STORE'S POSITION IN THE ALLOCATION SEQUENCE IS INVARIANT UNDER LAYOUT
  CHANGES. Across a 64-byte shift of every subsequent address, the corruption
  still lands on the entry IMMEDIATELY AFTER the username allocations, and the
  chain still breaks after 39 entries in both runs.
  So the foreign store happens at a FIXED POINT IN THE STARTUP SEQUENCE --
  right after the username is allocated -- rather than at a fixed wall-clock
  moment or a fixed address in the heap. That is a genuine new invariant and
  it strengthens the case that the writer is a specific piece of startup code
  reached at a specific point, not a stray asynchronous write.

## ONE RUN NOT EXPLAINED
  USERNAME='aa' (2 chars) produced NO chain-walk output at all -- neither a
  corrupt entry nor a clean termination. I do not know why and am not
  guessing. It may be that the process failed earlier, or that the walker's
  capture did not trigger. Recording it as an unexplained data point rather
  than omitting it.

## GUARDING AGAINST AN OVER-ELIMINATION: 'StackBase+8 IS DEAD TWICE' IS WRONG
  A reconciliation from another session concluded the StackBase+8 hypothesis
  was 'dead twice' -- once by measurement (__getreent correct) and once
  'geometrically', because StackBase+8 = 0x800000008 'only reaches the chain
  head, which is the right address but the mechanism doesn't produce it'.

  THE SECOND COUNT IS NOT AN ELIMINATION -- IT IS A MATCH, AND IT SUPPORTS THE
  HYPOTHESIS RATHER THAN KILLING IT. I measured that the main thread's
  StackBase IS 0x800000000, so cygheap+8 IS StackBase+8, to the byte. That
  exact coincidence is the strongest structural fact in favour of a
  StackBase-derived writer.

  WHAT IS ACTUALLY ELIMINATED IS __getreent SPECIFICALLY -- one consumer of
  StackBase, measured to read [x18+8], subtract 12800, and return 0x7ffffce00.
  ANY OTHER CODE HOLDING StackBase AND ADDING A SMALL POSITIVE OFFSET WOULD
  LAND ON THE CHAIN HEAD, and nothing measured rules that out.

     __getreent as the writer:            DEAD (measured)
     a StackBase-derived store generally: ALIVE, and the most mechanically
                                          plausible remaining shape

  RECORDED BECAUSE THE FAILURE MODE IS EXPENSIVE: 'dead twice' would close a
  live class on the strength of a fact that supports it. Prematurely-closed
  classes are worse than open ones -- an open class gets tested, a closed one
  does not. The right first question of any faulting PC remains: is the
  store's base register sp- or x18-derived?

## WINDOW REFINEMENTS CARRIED FORWARD
  Not 'between two adjacent cstrdup calls in set_name/cygheap_init': after the
  username cstrdup, user::init, init_installation_root and pg.init allocate NO
  HEAP_STR, so the next cstrdup is later, in memory_init. The interval spans
  the whole setup_cygheap tail. My bisection places a THREAD CREATION inside
  the bracket and NO DLL loads.

## A PROVENANCE ERROR ABOUT MY OWN EDIT, CORRECTED BEFORE IT ENTERED THE RECORD
  Another session reported: 'The port also wrote the static_assert at
  cygtls.h:313-329 predicting this exact failure -- StackBase+8 is exactly
  cygheap->chain -- BEFORE the bug was observed. The port author knew this was
  possible.'
  I WROTE THAT ASSERT AND THAT COMMENT TODAY, ABOUT NINETY MINUTES AGO, AFTER
  the bug was fully characterised. The quoted phrasing is mine, and I could
  only write it BECAUSE I had already measured StackBase == CYGHEAP_STORAGE_LOW
  == 0x800000000 and identified the corrupted slot.
  As reported it would have entered the record as evidence that the sealed
  port ANTICIPATED this defect. It is the opposite: a guard added in RESPONSE
  to it.
  THIS IS THE ARTEFACT-IDENTITY FAILURE ON THE SOURCE SIDE -- the same class as
  verifying a binary that was rebuilt underneath you. A tree that has been
  edited during an investigation will present today's conclusions as though
  they were yesterday's foresight, and nothing in the file says otherwise.
  RULE: WHEN CITING SOURCE AS PRIOR ART, ESTABLISH ITS AGE. In a tree under
  active edit, 'the code already says X' may mean 'someone said X an hour ago'.

## AND THE tlsoffsets LEAD, CHECKED AND CLOSED
  Claim: gentls_offsets greps '.long' while ARM64 GCC emits '.word', so the
  offsets were hand-generated and one may be wrong -- which would make asm
  writes land at a wrong address while C++ stayed correct.
  THE SCRIPT OBSERVATION IS CORRECT: scripts/gentls_offsets does grep .long
  (lines 65 and 88).
  THE OFFSETS ARE NEVERTHELESS RIGHT. Compared the generated file against a
  compiled probe of the real struct:
     tlsoffsets     _cygtls.initialized = -7792   _cygtls.initialized_p = 5008
     compiled       offsetof - PADSIZE  = -7792   offsetof              = 5008
                    sizeof(_cygtls) = 5016
  EXACT MATCH, 59 lines, self-consistent.
  AND THE SPECIFIC QUESTION ASKED -- is any offset +8, or reachable as +8 by a
  sign error? NO. Negative offsets run -7787..-7912; positive '_p' variants run
  4888..5013. Negating -7792 gives +7792, not +8. Nothing is near +8.
  RESIDUE WORTH KEEPING ON ITS OWN TERMS: the file is CORRECT but NOT
  REPRODUCIBLY REGENERABLE on this target, because the generator greps for a
  directive the compiler does not emit. That is a real latent build-system
  defect -- just not this bug.
