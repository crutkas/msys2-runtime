## THE NEW DATUM: WHAT SITS IMMEDIATELY BELOW THE DEEPEST CHAIN ENTRY
  Dumped memory around the deepest chain entry in a NON-FORKING process:

   0x8000068C0  00 00 00 00 00 00 00 00-B0 50 00 00 08 00 00 00
   0x8000068D0  01 00 00 00 00 00 00 00-00 00 00 00 00 00 00 00
   0x8000068E0  63 72 75 74 6B 61 73 4C-6F 63 61 6C 00 00 00 00  |crutkasLocal....|
   0x8000068F0  06 00 00 00 00 00 00 00-00 A0 2C 00 80 00 00 00  <== ENTRY, prev wild
   0x800006900  03 00 00 00 ...                                   (ce->type = 3)

  THE ALLOCATION IMMEDIATELY BELOW THE DEEPEST CHAIN ENTRY IS THE USERNAME
  STRING. That comes from cygheap->user.init(), called in setup_cygheap()
  immediately after cygheap_init(), via cstrdup -> cmalloc. SO IT IS A
  cmalloc'd ALLOCATION AND IT SHOULD BE ON THE CHAIN. IT IS NOT -- the
  chain's deepest entry is ABOVE it.

  CONCLUSION, AND IT IS TIGHTER THAN THE PREVIOUS ONE:
  cygheap->chain WAS CLOBBERED BETWEEN THE USERNAME ALLOCATION AND THE
  NEXT ONE. The next _cmalloc then stored the clobbered value as its
  prev, permanently truncating the chain AND leaving a wild pointer as
  its terminator. Everything allocated before that moment is orphaned.

## THREE HYPOTHESES KILLED

  1. MY OWN cygheap_dummy HYPOTHESIS -- DEAD.
     I proposed that an early _cmalloc, while cygheap still points at the
     8-byte cygheap_dummy, reads chain one word past the object. It cannot
     happen silently: at that point cygheap_max is NULL, so _csbrk takes
     'nothing to do' and RETURNS NULL, so _cmalloc RETURNS NULL, and
     dll_list::alloc (dll_init.cc:350) would dereference a null d and
     CRASH. No crash occurs. Therefore no pre-cygheap_init _cmalloc runs.
     A hypothesis that predicts a crash we do not observe is refuted.

  2. A BUFFER OVERRUN FROM THE PRECEDING ALLOCATION -- DEAD.
     The username string is NULL-TERMINATED WITHIN its 16 bytes, and more
     decisively the entry's b field at +0 is INTACT (b = 6, a valid
     bucket). A linear overrun running off the end of the string would
     corrupt +0 BEFORE it reached +8. Only +8 is wrong. Not an overrun.

  3. A WIDE WRITE THROUGH cygheap->locale -- DEAD.
     chain sits at +8, directly after locale at +0, so an oversized locale
     store would clobber it. Every write to cygheap->locale in the tree is
     an 8-byte pointer assignment (cygheap.cc:303, nlsfuncs.cc:1770/1772).
     sizeof(cygheap_locale) = sizeof(mini_cygheap) = 8, measured. There is
     no memcpy or memset targeting the cygheap header (the only memset is
     cygheap.cc:643, on threadlist). heap.cc:172 mentions cygheap_dummy but
     it is a COMMENT about strace output, not a write.

## WHAT REMAINS OPEN
  What writes 8 bytes at cygheap+8 between cygheap->user.init() and the
  next _cmalloc. The value is an mmap-arena pointer that varies per run,
  so the writer is storing a real, freshly-obtained address there.

## THE ptmalloc-SEGMENT HYPOTHESIS, TESTED AND PARTLY REFUTED
  A sibling re-classified the six wild values by GiB against memory_layout.h
  and CORRECTED MY REGION LABEL: they are NOT in the MMAP arena (which starts
  at 1024 GiB) but in the USER-HEAP GROWTH region, 512-887 GiB. That
  correction is right and I accept it. Their hypothesis: the value is a
  ptmalloc SEGMENT BASE from win32mmap/win32direct_mmap (mm/malloc.cc
  1670/1676), the only unbounded VirtualAlloc(0,...) calls in the tree.

  DISCRIMINATOR BUILT: two programs, identical but for one user malloc.
    rung9.c   -- NO user malloc, NO stdio (printf itself allocates), just a
                 deliberate fault as the capture mechanism.
    rung10.c  -- identical plus a single malloc(64)/free().

  RESULT -- rung9, WITH NO USER ALLOCATION AT ALL:
     cygheap->chain = 0x800021840
     [38] rvc=0x8000068F0  b=0x6  prev=0x000000C493967000  <== OUT OF CYGHEAP
     >>> CHAIN IS UNTERMINATED after 39 entries.  lowest entry 0x8000068F0
  IDENTICAL SIGNATURE. Same entry, same shape, wild terminator.

  SO THE CORRUPTION DOES NOT REQUIRE ANY APPLICATION ALLOCATION. It happens
  entirely inside Cygwin's own startup, before and independent of anything
  the program does. A program whose entire body is a null store already has
  a 39-entry corrupt chain.

  WHAT THIS DOES AND DOES NOT KILL -- STATED CAREFULLY:
   - It KILLS the form 'a user malloc triggers it'.
   - It DOES NOT kill the ptmalloc hypothesis itself, because the Cygwin
     runtime calls malloc internally during startup regardless of what the
     application does. Removing the application's malloc does not remove
     ptmalloc from the picture. I am not claiming it does.

## A REFINEMENT THAT ARGUES AGAINST 'SEGMENT BASE' SPECIFICALLY
  If the value were a ptmalloc SEGMENT BASE it should BE the base of a
  VirtualAlloc region. It is not. From the parent/child comparison run:
     bad value 0x80002D1000 -> VirtualQueryEx: COMMITTED allocBase=0x8000200000
  The value sits 0xD1000 bytes INTO a region based at 0x8000200000. So it is
  a POINTER INTO a heap region, not the base of one -- which is the shape of
  an ALLOCATED CHUNK POINTER rather than a segment base.
  DERIVED, not measured: I have not read ptmalloc's mstate to confirm what
  the region is, so 'chunk pointer' is an inference from the offset alone.

### 1. THE 'ONE INSERTED HEX DIGIT' THEORY IS REFUTED BY THE RAW CAPTURE.
  Claim: my values might be one digit too wide, and the real value might be
  0x800300000 = CYGHEAP_STORAGE_INITIAL rather than 0x80002CA000.
  RAW BYTES AS CAPTURED, no conversion, from the memory dump:
      00 A0 2C 00 80 00 00 00
  little-endian u64 = 0x00000080002CA000
      equals 0x80002CA000 ?  TRUE
      equals 0x800300000  ?  FALSE
  The read width is 8 bytes via ReadProcessMemory with an explicit length
  check (got == 8), and the value is reconstructed with BitConverter.ToInt64.
  THE VALUES ARE FULL WIDTH. The theory is dead.

### 2. THE SHARED '.003' FRACTION IS NOT A FINGERPRINT -- IT IS ARITHMETIC.
  The observation was that '.003 GiB' occurs exactly once in the layout, at
  CYGHEAP_STORAGE_INITIAL, and my values carry the same fraction.
  THAT IS TRUE BUT NOT DIAGNOSTIC:
      0x80002CA000 - 0x8000000000 = 0x2CA000 = 2.789 MiB -> .0027 GiB -> .003
      0x800300000  - 0x800000000  = 0x300000 = 3.000 MiB -> .0029 GiB -> .003
  ANY address roughly 3 MiB above a GiB boundary displays .003. The fraction
  is a property of the display precision, not of a shared constant. A
  coincidence at 3 significant figures is not a shared origin.

### RECONCILING THE TWO DATASETS
  CAPTURED HEAD WRITES (watchpoint):  0 -> 0x48A0 -> 0x50B0 -> [gap] -> 0x6A40 -> ...
  FINAL CHAIN WALK (head to tail):    ... 0x6A40 -> 0x6A00 -> 0x68F0 -> WILD
  0x6A40's prev is 0x6A00, not 0x50B0, so 0x6A00 and 0x68F0 were born in the
  gap. TRUE BIRTH ORDER: 0x48A0, 0x50B0, ..., 0x68F0, 0x6A00, 0x6A40, ...

### THE DECISIVE BYTES -- ALREADY IN MY POSSESSION, RE-READ
  0x8000068C0  00 00 00 00 00 00 00 00 - B0 50 00 00 08 00 00 00
  0x8000068D0  01 00 00 00 ...
  0x8000068E0  63 72 75 74 6B 61 73 4C - 6F 63 61 6C 00 00 00 00   |crutkasLocal|
  0x8000068F0  06 00 00 00 00 00 00 00 - 00 A0 2C 00 80 00 00 00   <== WILD

  THERE IS AN INTACT _cmalloc_entry AT 0x8000068C0:
     b    = 0            (bucket 0 = 32 bytes)
     prev = 0x8000050B0  <-- EXACTLY the previous head my watchpoint captured
     data = 0x8000068D0, and the username string follows at 0x8000068E0
  GEOMETRY CONFIRMS IT: 0x68C0 + 16 (header) + 32 (bucket 0) = 0x8000068F0,
  which abuts the wild entry exactly. This is the username allocation and it
  is CORRECTLY CHAINED to 0x50B0.

### THEREFORE
  Entry 0x8000068C0 (username) was born with a CORRECT prev.
  Entry 0x8000068F0, THE VERY NEXT ALLOCATION, was born with a WILD prev.
  Entry 0x800006A00's prev is 0x68F0 -- correct again.
  ONLY ONE ENTRY IS WRONG, AND IT IS THE ONE IMMEDIATELY AFTER THE USERNAME.

  THE CLOBBER OF cygheap->chain HAPPENS BETWEEN THE BIRTH OF THE USERNAME
  ENTRY AND THE BIRTH OF THE NEXT ENTRY. The head was valid (0x68C0) at the
  first, wild at the second, and valid again immediately after (because
  0x68F0 became the head and 0x6A00 chained to it correctly).
  IT IS A SINGLE, ONE-TIME, 8-BYTE STORE TO cygheap+8.

### I RETRACT MY RETRACTION, AND NAME WHY IT WAS WRONG
  I originally stated this window -- 'between the username allocation and the
  very next one' -- and then WITHDREW it on a timing argument: that the mmap
  arena does not exist during setup_cygheap, so an mmap address could not be
  stored then. The bytes now say the window was right all along.
  SO THE TIMING ARGUMENT HAS A FALSE PREMISE SOMEWHERE. Either the username
  allocation is NOT where we assumed in the startup sequence, or mmap-arena
  addresses exist earlier than assumed. I have not determined which, and that
  is now the sharpest open question -- it is a contradiction between two
  pieces of evidence, not a gap.
  METHOD NOTE AGAINST MYSELF: I withdrew a correct, measurement-backed claim
  in favour of an argument from source-reading. The bytes outrank the
  narrative, and I should have said 'these conflict' rather than yielding.
