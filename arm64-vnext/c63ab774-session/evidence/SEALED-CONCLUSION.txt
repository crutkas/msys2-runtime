## 1. MECHANISM: DERIVED, NOT OBSERVED.
   MEASURED: the stored value is the main thread's TEB exactly (difference
   zero, many runs); the store target is cygheap+8, which IS StackBase+8
   (main StackBase == 0x800000000 == CYGHEAP_STORAGE_LOW, measured).
   DERIVED: since NT_TIB.StackBase lives at TEB+8, those two facts are
   explained by a single-thread direction inversion --
        *(StackBase+8) = TEB     where the correct idiom is
        StackBase = *(TEB+8)
   NO INSTRUCTION PERFORMING THIS HAS BEEN OBSERVED. No PC, no opcode, no
   register pair. cygheap->chain is collateral: it merely occupies that
   address.

## 3. CONTRIBUTING FACTOR: MEASURED -- AND NOT A REMEDY.
   THREAD_STORAGE_HIGH == CYGHEAP_STORAGE_LOW == 0x800000000, so the main
   thread's StackBase IS the cygheap base. That coincidence is what turns an
   inverted store into cygheap corruption rather than a harmless write.
   RELOCATING THE CYGHEAP IS NOT AN AVAILABLE MITIGATION -- TESTED, BREAKS THE
   RUNTIME OUTRIGHT. Moving CYGHEAP_STORAGE_LOW to 0x900000000 produced a
   clean NULL-terminated chain AND made every rung abort with 0x80000001; the
   chain was clean only because the process died after three allocations
   instead of thirty-nine. The fixed base is load-bearing beyond the layout
   header.

## AMENDMENT (later same day) -- LINE 3 STRENGTHENED.
   Contributed by session 57224227, verified independently here against
   memory_layout.h:33-47 and create_posix_thread.cc:134/230/274.

   The StackBase/cygheap aliasing is NOT a coincidence. It is EXACT BY
   CONSTRUCTION:
       thread_allocator () : current (THREAD_STORAGE_HIGH)   // seeded AT cygheap base
       addr = current - real_size                            // grows DOWNWARD
       StackBase = allocationbase + stacksize                // adds the size back
   For the FIRST allocation (the main thread stack, before any pthread):
       StackBase = (THREAD_STORAGE_HIGH - real_size) + stacksize
   which cancels to THREAD_STORAGE_HIGH exactly whenever real_size == stacksize.
   MEASURED on rung10.exe: SizeOfStackReserve = 0x200000 (2 MB);
   roundup2(.,THREAD_STACK_SLOT=1MB) = 0x200000; roundup2(.,64K) = 0x200000.
   EQUAL -> StackBase == THREAD_STORAGE_HIGH == CYGHEAP_STORAGE_LOW
         == 0x800000000, identical to the measured value.
   CONDITION (not unconditional): a reserve that is not a whole number of
   1 MB slots would make the two roundings disagree and shift StackBase
   below the boundary. The measured 2 MB satisfies it.

   CONSEQUENCE -- RELOCATION CAN NEVER DECOUPLE THEM. main StackBase is
   THREAD_STORAGE_HIGH; the cygheap base is CYGHEAP_STORAGE_LOW; the design
   DEFINES those two constants equal. Any correct coordinated re-partition
   moves both together and the aliasing SURVIVES the move. The two addresses
   are the same symbol. Decoupling requires inserting a gap between the
   arenas -- breaking the layout's contiguity invariant, not changing its
   addresses.

   WHY MY EARLIER RELOCATION BROKE (root cause, not just symptom): I moved
   CYGHEAP_STORAGE_LOW alone, leaving THREAD_STORAGE_HIGH, CYGHEAP_STORAGE_HIGH
   and USERHEAP_START behind -- opening an unowned gap 0x800000000-0x900000000,
   halving the cygheap arena, and stranding the main stack on the old boundary.
   A one-constant edit to a value four other constants abut.

   NET: 'relocate the cygheap' is dead as a mitigation on TWO independent
   grounds -- it breaks the runtime empirically, AND it cannot remove the
   aliasing even done correctly. The real fix remains the direction-inversion
   store itself, which is still UNNAMED (line 4 unchanged).
