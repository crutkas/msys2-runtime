## 1. THE FIX (dcrt0.cc, aarch64 arm of the stack switch)
   was:  mov sp, %[ADDR] ; mov x29, sp
   now:  mov sp, %[ADDR] ; sub sp, sp, #64 ; mov x29, sp
   The false rationale in the comment ("no shadow space, so nothing has to
   be subtracted") was replaced with the measured reason.

## 2. SUBTRACTION SIZE MEASURED, NOT ASSUMED
   Every sp-relative access in _dll_crt0 (67 lines disassembled):
     [sp]  [sp,#24]  [sp,#-32]
   Max POSITIVE offset = 24; the store is 8 bytes wide => reach = 32 bytes.
   Headroom above sp before StackBase was 16.  Overrun = 16 bytes.
   Chosen subtraction 64 > 32 required, and 64 keeps sp 16-byte aligned
   (AArch64 requires it).  x86's 32 was NOT copied blindly.

## 11. IS THERE A SECOND INSTANCE?  SOURCE-LEVEL SWEEP -- NO.
   Grepped all of winsup/cygwin for inline asm that WRITES sp (reads are
   harmless: cygtls.h:363 and fork.cc:671 only read it).  Exactly three
   sites write sp, including the one fixed here.

   (a) exceptions.cc:1991-2010  signal alternate-stack switch -- CORRECT.
         sub x9, x9, #32      // room for old sp and fp  <-- EXPLICIT HEADROOM
         str x15, [x9] ; str x29, [x9,#8] ; mov sp, x9 ; blr x14
         ldr x29,[sp,#8] ; ldr x15,[sp]   // restores inside the 32 reserved
       The SAME port author DID reserve headroom here.  So the dcrt0.cc
       omission was SITE-SPECIFIC, not a systematic misunderstanding of the
       AArch64 ABI.  Recorded because it changes the character of the defect.

   (b) create_posix_thread.cc:103-118  pthread_wrapper -- LATENT ONLY.
       Carries the IDENTICAL false rationale ("Windows ARM64 has no shadow
       space, so nothing to reserve"), but is safe by arithmetic rather than
       by design: sp lands at stackbase - __CYGTLS_PADSIZE__ (12800 bytes
       below), so any positive-offset spill would land in _cygtls, NOT the
       cygheap, and the only compiler code after the block is an unreachable
       api_fatal().  Not a bug; flagged because the misconception is the same
       and the safety is accidental.

   (c) dcrt0.cc  -- the one fixed in this file.

   CONCLUSION: the dangerous shape -- a hand-written sp write with
   insufficient headroom FOLLOWED BY compiler-generated code using positive
   sp offsets -- occurs exactly ONCE in the runtime, and it is fixed.

   FALSIFIER, stated so it can be tested against the binary rather than

## 12. SECOND DEFECT FIXED -- argv CORRUPTION (overlapping strcpy)
   Reported by supervisor 290c9aaf, who also validated the fork fix at 7/7 on
   their P3 fixture (first from-source validation; their prior confirmations
   were binary patches).  Verified independently here before applying.

   THE DEFECT: dcrt0.cc quoted() lines 165/167 do
       strcpy (cmd, cmd + 1);          and     strcpy (p, p + 1);
   Destination and source OVERLAP (dst = src-1), which is undefined behaviour.
   x86_64's byte-forward strcpy happens to produce the intended left-shift;
   AArch64's reads 16-byte NEON blocks from a down-aligned source and re-reads
   bytes its own stores already overwrote.  Tree-wide sweep: EXACTLY these two
   sites.  Upstream Cygwin latent bug that the ARM64 port merely exposes.

   REPRODUCED INDEPENDENTLY BEFORE FIXING (DLL 54e464d0, rung13):
     sent  "abcdefghijklmnopqrstuvwx"
     got   "abcdefghijmnopqrstuuvvwx"   <- "kl" dropped, "u" and "v" doubled
   Note the length is still 24, so a length check alone would NOT catch it.

   FIX: memmove, which is defined for overlapping regions.
     memmove (cmd, cmd + 1, strlen (cmd + 1) + 1);
     memmove (p, p + 1, strlen (p + 1) + 1);
   Verified 2 bl <memmove> in the rebuilt dcrt0.o.  tlsoffsets guarded and
   INTACT (49ac682b8f5e both sides).

   AFTER (DLL 90bfb483ae44aea20f3f9491bd42d92b1c3233cdf1b35fac580f9791d4dea310):
     all three probe strings round-trip exactly; VERDICT ALL ARGS INTACT.
   LENGTH SWEEP, because the corruption position tracks command-line length:
     quoted argument of EVERY length 1..40, round-tripped and compared
     byte-for-byte -> 40 tested, 0 mismatches.
   REGRESSION, same run: rung3 77 / rung4 42 / rung5a 55 / rung6 66 /
     rung7 44 / rung12 88 "ALL PASS (0 failures)".  No regression.

   Combined patch for both dcrt0.cc fixes: evidence/dcrt0-both-fixes.patch

## 14. NEON MECHANISM: DERIVED WHEN COMMITTED, MEASURED AFTERWARDS -- A LAPSE.
   Commit 6397acaa5 states as fact: "AArch64's strcpy aligns the source down
   to a 16-byte boundary and loads NEON blocks."  At the time I wrote that I
   had NOT disassembled aarch64 strcpy.  I took it from a report.  The
   verifier had explicitly labelled it "DERIVED, NOT MEASURED -- I have not
   disassembled the aarch64 strcpy" and asked that it not be recorded as
   established.  I recorded it as established, in a permanent commit message.

   IT WAS SUBSEQUENTLY MEASURED and is true.  Session 57224227 disassembled
   the strcpy the DLL links:
       ld1  {v0.16b}, [x2]        ; 16-byte block load
       cmeq v1.16b, v0.16b, #0    ; NUL scan
       shrn v2.8b,  v1.8h, #4
       ldr  q0, [x2, #16]!        ; next 16-byte block
   That is exactly an implementation that re-reads source bytes its own
   stores have overwritten when the regions overlap.

   RECORDED AS A LAPSE ANYWAY, because the order was wrong: verification
   arrived after the durable claim.  The fix never depended on the mechanism
   -- the UB is sufficient justification and memmove is correct regardless of
   why strcpy misbehaves -- which is the only reason this is a lapse and not
   a retraction.

   BEHAVIOUR PRESERVATION (from 57224227, worth foregrounding for upstream):
   memmove (dst, dst+1, strlen (dst+1) + 1) is semantically identical to what
   the buggy strcpy was intended to do, so x86_64 behaviour is provably
   unchanged.  A UB fix that cannot regress already-shipped platforms is the
   first thing an upstream maintainer will ask about.

   OPEN, DELEGATED TO 57224227: sweep for adjacent overlapping-copy idioms --
   memcpy on self-overlap; strcat/stpcpy/strncpy writing into their own
   source; and the shape MY grep would have missed, a left-shift through a
   VARIABLE offset (strcpy (p, p + n)) rather than the literal "+ 1" I
   pattern-matched on.  Scoped deliberately to SYNTACTIC self-reference:
   overlap through distinct pointers into one buffer needs aliasing analysis
   and is out of scope, so the result must be recorded as a BOUNDED negative.
