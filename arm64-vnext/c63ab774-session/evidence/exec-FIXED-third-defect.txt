## THE DEFECT
   dcrt0.cc child_info_spawn::handle_spawn():
       if (!dynamically_loaded || get_parent_handle ())
         { cygheap_fixup_in_child (true); memory_init (); }
   On a normal exec dynamically_loaded is FALSE, so !dynamically_loaded is
   TRUE and C short-circuit evaluation means get_parent_handle() IS NEVER
   CALLED.  cygheap_fixup_in_child then uses the INHERITED parent handle.

## MEASURED WITH INSTRUMENTATION (not inferred)
   Built a DLL that reports the state at that exact point:
     EXP: dynamically_loaded=0 parent=0x19C usable=0 err=6
          parent_winpid=22704 short_circuits=1
     EXP: reopen=1 newparent=0x114 usable=0 err=5
   Reading, line by line:
     - dynamically_loaded=0 and short_circuits=1  -> get_parent_handle() is
       indeed never reached on the exec path.  The verifier's static reading
       is confirmed dynamically.
     - the INHERITED parent handle is UNUSABLE: err=6 ERROR_INVALID_HANDLE.
       That is the same error child_copy reports.
     - reopen=1: OpenProcess(PROCESS_VM_READ, FALSE, parent_winpid) SUCCEEDS.
     - "usable=0 err=5" on the REOPENED handle is MY INSTRUMENT BEING WRONG,
       not a bad handle: I probed with GetExitCodeProcess, which needs
       PROCESS_QUERY_INFORMATION, and the handle was opened with only
       PROCESS_VM_READ.  ReadProcessMemory needs exactly PROCESS_VM_READ,
       which is why child_copy then succeeds.  Recorded because a reader
       would otherwise take err=5 as evidence against the fix.

## THE FIX (minimal): call get_parent_handle() unconditionally

   parent_winpid is set unconditionally at spawn.cc:602, outside the
   if (!iscygwin ()) block -- precondition verified in the live tree.

## THREE CAVEATS -- THIS IS NOT A ROOT-CAUSE FIX
   1. WHY the inherited parent handle is invalid on AArch64 is NOT explained.
      This repairs the symptom by taking a recovery path that already exists.
      The upstream assumption "the inherited handle is usable on the normal
      exec path" is false here, and nobody has said why.
   2. BEHAVIOUR CHANGE ON OTHER TARGETS: every exec now performs an extra
      OpenProcess.  Where the inherited handle was already good this replaces
      it with an equivalent one.  Cheap, but not zero.
   3. HANDLE LEAK, PRE-EXISTING BUT NOW ON EVERY EXEC: get_parent_handle()
      overwrites 'parent' without CloseHandle on the old value.  That leak
      already existed on the dynamically_loaded path; this change makes it
      happen on every exec.  Short-lived (process transition), but real, and
      a proper fix should close the old handle first.

## APPENDED -- HANDLE LEAK CLOSED (coordinator item 1)
   The minimal fix left get_parent_handle() overwriting 'parent' without
   CloseHandle -- a leak that pre-existed on the dynamically_loaded path and
   which the fix moved onto EVERY exec.  Now closed inside the function, so
   BOTH call sites benefit:

     HANDLE prev = parent;
     parent = OpenProcess (PROCESS_VM_READ, FALSE, parent_winpid);
     if (parent && prev && prev != parent)
       CloseHandle (prev);
     return !!parent;

   Deliberately closes ONLY on success, so the failure path keeps upstream's
   exact behaviour (parent NULL, return false) rather than inventing new
   semantics in a fix that is already going around a root cause.
