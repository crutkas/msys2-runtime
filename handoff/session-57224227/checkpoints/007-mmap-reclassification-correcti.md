<technical_details>
- **THE BUG (current understanding):** `cygheap->chain` (at `cygheap+8` = `0x800000008`) is clobbered to an MMAP-arena pointer during Cygwin's OWN startup (no app allocation needed — rung9 proves it). The chain becomes unterminated; walking it (fork's `cygheap_fixup_in_child`, or any walk) dereferences a wild `prev`. The head STARTS correct (`0→0x48A0→0x50B0`, MEASURED by c63ab774's watchpoint) and becomes wild later. The `crutkasLocal` username entry at `0x8000068F0` is orphaned (not on the chain), `b`=6 intact at +0, `prev`@+8 wild.
- **CORRECTED wild-value classification (MEASURED from primary source):** `MMAP_STORAGE_LOW = 0x001000000000` = **64 GiB**; `MMAP_STORAGE_HIGH = 0x700000000000` = 114688 GiB. All nine observed wild values are INSIDE this arena: `0xBD102AE000`=756.3G, `0xDDC4F01000`=887.1G, `0xC493967000`=786.3G, `0xE0A3FDF000`=898.6G, and five clustered at exactly `512.003 GiB` (`0x80002D1000`/`0x8000316000`/`0x80002CA000`/`0x8000351000`/`0x8000384000`). **My earlier "user-heap growth region" reclassification (checkpoint 009) was a factor-of-16 typo (`0x10000000000`) and is WRONG.** c63ab774's original MMAP-arena label was correct.
- **c63ab774's chunk refinement (DERIVED):** `0x80002D1000` sits `0xD1000` into a COMMITTED region based at `0x8000200000` (512 GiB) — the shape of an allocated heap-CHUNK pointer, not a segment base. c63ab774 labelled this derived (hasn't read the mstate).
- **THE DISCRIMINATOR (handed by c63ab774, exact reads provided):** `_gm_` is `.bss`, `offsetof(malloc_state, seg)=888`; `struct malloc_segment = {char* base@0; size_t size@8; msegment* next@16; flag_t sflags@24}`. Read `seg.base = *(void**)((char*)&_gm_ + 888)`, `seg.size` at +896, walk `seg.next` at +904. If a wild value V satisfies `base <= V < base+size` for some segment → V is a dlmalloc CHUNK pointer; if V == a seg.base exactly → segment base. This is c63ab774's to execute (dynamic).
- **ALLOCATOR STRUCTURE (MEASURED, cygheap.cc):** `_cmalloc` chains an entry ONLY on the fresh-`_csbrk` path (:396-398: `rvc->prev = cygheap->chain; cygheap->chain = rvc`). On freelist reuse (:381-386) it writes only `rvc->ptr`/`rvc->b` at +0, does NOT re-chain, does NOT touch +8. `_cfree` (:410) threads the freelist through +0 (`rvc->ptr`), NEVER +8, NEVER unlinks from the chain. So entries are chained once at birth and never removed; chain(+8) and freelist(+0) are disjoint fields. => the allocator CANNOT clobber the head; the head clobber is a FOREIGN store.
- **`cygheap` global is stable (MEASURED):** only ever assigned `&cygheap_dummy` (cygheap.cc:35) or `VirtualAlloc(CYGHEAP_STORAGE_LOW)` (cygheap.cc:92/96/293/297). Never transiently mis-points. So `:398`'s target `cygheap->chain` is always `0x800000008`.
- **EMUTLS — KILLED BY MEASUREMENT for the runtime:** Compiler DOES use emutls (`__thread` probe emits `bl __emutls_get_address`; gcc `--disable-threads`; emutls.c single-threaded path stores `malloc()` return into `obj->loc.ptr`). BUT the runtime never uses it: Cygwin source has ZERO `__thread`/`_Thread_local`; 273 built objects (recursive, incl mm/) + `new-msys-2.0.dll` + `new-msys-2.0-fixedbase.dll` have ZERO `__emutls_get_address` refs / `__emutls_v` objects / 'emutls' strings. Objects NOT stripped (verified: cygheap.o has normal U symbols, DLL has 288k symbols). Also DWARF: `sizeof(__emutls_object)=32`, `size@0, align@8, loc@16, templ@24` — the malloc store lands at obj+16 anyway, not +8. If c63ab774's actual link pulls emutls.o into the DLL, that's a config discrepancy to reconcile, but it's absent in the tree measured here.
- **THE 0x2050 GAP (partial, not reported):** x86-64 first chain entry = `cygheap+sizeof(init_cygheap)=0x48A0`; ARM64 lowest SURVIVING entry = `0x68F0` (`0x2050`=8272 bytes higher). Note this is the lowest surviving (post-corruption), not necessarily the first-ever. Early setup allocations in order: `cygheap_init` (fdtab.init → sigalloc → init_tls_list), then `user.init()` (username cstrdup = the 0x68F0 entry). Measured pieces: `threadlist_t={_cygtls* thread; HANDLE mutex}`=16B (LP64-same); `THREADLIST_CHUNK=256` → init_tls_list allocates 256*16=4096=`0x1000`; `sigalloc` = `_NSIG*sizeof(sigaction)`; fdtab `extend(NOFILE_INCR,0)`.
